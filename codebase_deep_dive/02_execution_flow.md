# 02 — Execution Flow

## Purpose

This file traces how an OpenBBPort command moves through the system from user call to provider fetch and back to an `OBBject`. It covers both the Python SDK and REST API surfaces.

## The two main entry paths

OpenBBPort exposes commands through two primary surfaces:

1. **Python SDK path**
   - user imports `from openbb import obb`
   - generated SDK methods are mixed into the `obb` app object
   - SDK methods call `self._run(...)`
   - `_run(...)` delegates to `CommandRunner`

2. **REST API path**
   - FastAPI app is created in `openbb_core.api.rest_api`
   - extension routes are loaded and wrapped in `openbb_core.api.router.commands`
   - HTTP request parameters are converted into command kwargs
   - wrapper delegates to `CommandRunner`

Both paths converge at `CommandRunner` and then continue through `Query`, `QueryExecutor`, and provider fetchers.

## Python SDK boot flow

### 1. Importing `openbb`

Path: `openbb_platform/core/openbb/__init__.py`

Import flow:

```text
import openbb
  -> instantiate PackageBuilder
  -> auto_build if enabled
  -> load reference metadata
  -> import generated Extensions class if present
  -> create app object via create_app(Extensions)
  -> expose obb/sdk
```

The import attempts to load:

```text
openbb.package.__extensions__.Extensions
```

When that import succeeds, the app becomes:

```text
class App(BaseApp, Extensions): ...
```

When it fails, the app becomes a base-only object and prints that extensions failed to import.

### 2. App object construction

Path: `openbb_platform/core/openbb_core/app/static/app_factory.py`

`BaseApp.__init__`:

1. initializes logging through `CommandRunner`
2. stores the command runner
3. builds coverage object
4. reads reference metadata

The app exposes:

- `obb.user`
- `obb.system`
- `obb.coverage`
- `obb.reference`

### 3. Generated SDK method call

Generated SDK modules are created by `PackageBuilder`. A generated method eventually calls:

```text
self._run(route, **filter_inputs(...))
```

The route is a normalized OpenBB command path such as:

```text
/equity/price/historical
```

The generated method handles provider argument selection, parameter filtering, dependency injection where safe, deprecation wrappers, charting argument insertion, and function signature ergonomics.

## REST API boot flow

### 1. FastAPI app creation

Path: `openbb_platform/core/openbb_core/api/rest_api.py`

The app is configured from system settings:

- title
- description
- version
- terms of service
- contact info
- license info
- server list
- CORS
- startup banner

Router inclusion differs by environment:

- In dev mode, auth, system, coverage, and commands routers are included.
- Outside dev mode, commands and coverage routers are included depending on available routes.

### 2. Command route wrapping

Path: `openbb_platform/core/openbb_core/api/router/commands.py`

At import time, this module:

1. creates an API router
2. creates `CommandRunner`
3. loads extension routes through `RouterLoader.from_extensions()`
4. wraps each route endpoint with `build_api_wrapper(...)`
5. includes the wrapped extension routes into the API router

The wrapper adapts router command functions for HTTP semantics.

It handles:

- endpoint signature reconstruction
- chart parameter injection when charting is installed
- custom header injection from system settings
- authenticated user settings when API auth is enabled
- user command defaults
- standard and extra param extraction
- FastAPI dependency transfer
- output validation or JSON serialization

### 3. API wrapper execution

A REST request enters the wrapper, which:

1. resolves user settings
2. loads per-command defaults from user settings
3. merges standard and extra params
4. handles route dependencies
5. calls `command_runner.run(path, user_settings, *args, **kwargs)`
6. serializes the result

Important branch:

- If output is an `OBBject` and an extension modified it, the wrapper bypasses normal response-model validation and serializes manually.
- If an extension marks `results_only`, the wrapper returns only the `results` content.
- If `no_validate` is not set, the wrapper validates output and strips API-excluded fields.

## Common command execution path

Both SDK and REST converge here:

```text
CommandRunner.run(route, user_settings, *args, **kwargs)
```

Path: `openbb_platform/core/openbb_core/app/command_runner.py`

### 1. Execution context creation

`CommandRunner.run(...)` creates an `ExecutionContext` containing:

- `CommandMap`
- route path
- system settings
- user settings

`ExecutionContext.api_route` resolves the FastAPI route from a route map generated by `PathHandler.build_route_map()`.

### 2. Command resolution

`StaticCommandRunner.run(...)` asks the command map for the function bound to the route.

If no function is found, it raises:

```text
AttributeError("Invalid command : route=...")
```

### 3. Parameter build and validation

`ParametersBuilder.build(...)` performs these steps:

1. **Polish function signature**
   - removes `__authenticated_user_settings` if present

2. **Merge args and kwargs**
   - positional args override by parameter position
   - kwargs fill named params
   - defaults fill missing values
   - variadic kwargs are merged back into the parameter map

3. **Inject command context**
   - if the command function accepts `cc`, it receives a `CommandContext` containing user and system settings

4. **Validate/coerce kwargs**
   - builds a runtime Pydantic model from the function signature
   - allows extra fields for command-context use cases
   - warns when unknown extra params are ignored by provider validation

This stage is a major behavioral boundary. Any change to function annotations, generated dataclasses, provider params, or FastAPI dependencies can affect command execution here.

### 4. Function execution

`StaticCommandRunner._execute_func(...)` then:

1. captures warnings
2. preserves raw kwargs for charting and metadata use
3. removes `chart` before validation
4. builds validated kwargs
5. removes API-only custom header values
6. calls `_command(...)`

`_command(...)` calls the command function, awaiting it when necessary. If the result is an `OBBject`, it attaches the selected provider.

### 5. OBBject post-processing

When the result is an `OBBject`, the runner attaches internal state:

- `_route`
- `_standard_params`
- `_extra_params`

If charting is requested and results exist, chart params are restored from raw kwargs and `obbject.charting.show(...)` is called if the charting accessor exists.

### 6. Warnings, logging, metadata

The runner then:

- stores captured warnings on the `OBBject`
- displays warnings if user preferences allow it
- logs the command unless logging is suppressed
- injects metadata when user preferences request metadata
- removes dependency-injection callables and unserializable values from metadata

### 7. Command-output callbacks

`StaticCommandRunner._trigger_command_output_callbacks(...)` uses `ExtensionLoader().on_command_output_callbacks` to run OBBject extension callbacks for:

- all routes via `*`
- the specific route path

Callbacks can be mutable or immutable. Mutable callbacks mark the result as extension-modified. Extensions can also mark output as `results_only`.

This is important for REST serialization because extension-modified output may bypass normal schema validation.

## Query execution path

Most route functions are intentionally thin. Example pattern from equity routes:

```text
async def historical(cc, provider_choices, standard_params, extra_params) -> OBBject:
    return await OBBject.from_query(Query(**locals()))
```

### 1. Query initialization

Path: `openbb_platform/core/openbb_core/app/query.py`

The `Query` object stores:

- `cc` command context
- selected provider from `provider_choices`
- standard params dataclass
- extra params dataclass
- model name from the standard params dataclass class name
- provider interface instance

For `EquityHistorical`, the query model name is derived from the dataclass name.

### 2. Extra parameter filtering

`Query.filter_extra_params(...)` compares provider-specific extra params against the provider metadata.

Behavior:

- If an extra param differs from its default and the selected provider supports it, include it.
- If it differs from default and the selected provider does not support it, emit an `OpenBBWarning`.
- If it equals default, avoid sending it to provider execution.

This prevents one provider's extra params from leaking into another provider's fetcher.

### 3. Query executor dispatch

`Query.execute(...)`:

1. converts standard params to dict
2. filters extra params
3. creates a `QueryExecutor`
4. calls `query_executor.execute(...)` with:
   - provider name
   - model name
   - merged params
   - user credentials
   - user preferences

## Provider execution path

Path: `openbb_platform/core/openbb_core/provider/query_executor.py`

`QueryExecutor.execute(...)` performs:

1. `get_provider(provider_name)`
2. `get_fetcher(provider, model_name)`
3. `filter_credentials(...)`
4. `fetcher.fetch_data(...)`

### Provider lookup

Providers are stored in the registry by lowercased provider name. If a provider is missing, execution raises an `OpenBBError` listing available providers.

### Fetcher lookup

Each provider exposes a `fetcher_dict`. The selected model must exist in this dictionary. If not, execution raises an `OpenBBError`.

### Credential filtering

Provider credentials are normalized by provider name in `Provider.__init__`. For example, a provider named `fmp` requiring `api_key` stores the credential key as:

```text
fmp_api_key
```

If a fetcher requires credentials and a required credential is missing, execution raises an `OpenBBError` with provider setup guidance.

### Fetcher pipeline

Path: `openbb_platform/core/openbb_core/provider/abstract/fetcher.py`

Every fetcher follows:

```text
transform_query(params)
  -> extract_data(query, credentials, **kwargs)
  -> transform_data(query, data, **kwargs)
```

If `aextract_data` is implemented, it replaces `extract_data` during subclass initialization.

This design lets providers implement sync or async data extraction while exposing one async `fetch_data(...)` method to the executor.

## Result wrapping

Path: `openbb_platform/core/openbb_core/app/model/obbject.py`

`OBBject.from_query(...)` awaits the query and wraps the provider result.

If the provider returns an `AnnotatedResult`, metadata is placed in:

```text
extra["results_metadata"]
```

Otherwise, returned data becomes:

```text
results=<provider result>
```

The command runner later adds provider attribution, route metadata, warnings, and optional command metadata.

## Representative end-to-end example: equity historical via yfinance

### Source components

- Router package: `openbb_platform/extensions/equity`
- Command route: `openbb_platform/extensions/equity/openbb_equity/price/price_router.py`
- Standard model: `openbb_platform/core/openbb_core/provider/standard_models/equity_historical.py`
- Provider package: `openbb_platform/providers/yfinance`
- Provider fetcher: `openbb_platform/providers/yfinance/openbb_yfinance/models/equity_historical.py`

### Flow

```text
obb.equity.price.historical(symbol="AAPL", provider="yfinance")
  -> generated SDK method
  -> self._run("/equity/price/historical", ...)
  -> CommandRunner.run(...)
  -> command map resolves price_router.historical
  -> ParametersBuilder validates provider/standard/extra params
  -> historical(...) returns OBBject.from_query(Query(**locals()))
  -> Query.execute()
  -> QueryExecutor.execute(provider_name="yfinance", model_name="EquityHistorical")
  -> yfinance provider fetcher_dict["EquityHistorical"]
  -> YFinanceEquityHistoricalFetcher.fetch_data(...)
  -> transform_query: defaults dates, validates interval/action/adjustment fields
  -> extract_data: calls yfinance helper download
  -> transform_data: validates rows as YFinanceEquityHistoricalData
  -> OBBject(results=[...])
  -> CommandRunner attaches provider, warnings, metadata, callbacks
  -> SDK returns OBBject
```

## REST version of the same command

```text
GET /equity/price/historical?symbol=AAPL&provider=yfinance
  -> FastAPI route wrapper
  -> user settings/defaults/header/auth handling
  -> CommandRunner.run("/equity/price/historical", ...)
  -> same query/provider execution as SDK
  -> output validation/serialization
  -> HTTP response
```

## Key execution invariants

These are core assumptions the system depends on:

1. Router command model names must match provider fetcher dictionary keys.
2. Provider fetchers must inherit from `Fetcher[QueryParamsType, ReturnType]` correctly so type extraction works.
3. Standard query/data models must inherit from the correct OpenBB abstract classes.
4. Provider-specific query/data models must cleanly extend standard models.
5. Generated SDK signatures must remain compatible with command function signatures.
6. Provider extra params must not leak into unsupported providers.
7. `OBBject` output must remain serializable after extension callbacks, charting, and metadata injection.
8. REST wrappers and SDK-generated methods must pass equivalent command semantics through `CommandRunner`.

## Failure points to watch

### Signature mismatch

If a command declares a `model=...` but does not include the expected `provider_choices`, `standard_params`, and `extra_params` annotations, `SignatureInspector.validate_signature(...)` raises an exception.

### Provider schema collision

ProviderInterface merges standard and extra fields across providers. Similar field names with different semantics, aliases, or incompatible types can produce confusing generated schemas.

### Defaults divergence

REST wrappers apply user command defaults differently from direct SDK generation. Regression tests should verify equivalent behavior across SDK and API where the command is supposed to be equivalent.

### Extension-modified output

OBBject output callbacks can mutate results and change REST serialization behavior. That is powerful but creates a bypass around normal response-model validation.

### Chart path coupling

Chart behavior is inserted by checking route-derived function names against charting functions. Rename or path changes can silently break chart availability.

### Import/build side effects

`openbb` import can trigger auto-build behavior depending on environment settings. This creates coupling between installation state, generated artifacts, and runtime import behavior.

## Testing implications

The correct testing approach is layered:

1. **Fetcher contract tests**
   - `transform_query`
   - `extract_data` mocked
   - `transform_data`
   - output validates as expected data model

2. **ProviderInterface tests**
   - merged standard params
   - merged extra params
   - provider choices
   - return schema generation
   - Literal/choice propagation

3. **Router tests**
   - model-bound command signature injection
   - command map generation
   - nested router path resolution

4. **CommandRunner tests**
   - kwargs merging
   - context injection
   - warning capture
   - metadata injection
   - callback execution

5. **SDK generation tests**
   - generated method signatures
   - provider argument handling
   - route names
   - docstrings where expected

6. **REST wrapper tests**
   - request parameter shape
   - default command values
   - auth injection
   - custom headers
   - extension-modified output
   - no-validate routes

## Condensed sequence diagram

```text
User / HTTP Client
  -> SDK method or FastAPI wrapper
  -> CommandRunner
  -> ParametersBuilder
  -> Router command function
  -> Query
  -> ProviderInterface
  -> QueryExecutor
  -> Provider
  -> Fetcher.transform_query
  -> Fetcher.extract_data / aextract_data
  -> Fetcher.transform_data
  -> OBBject.from_query
  -> CommandRunner post-processing
  -> SDK return or REST response
```

## Bottom line

The system is best understood as a dynamic command bus. Routers define commands, providers define implementations, and the core runtime binds them together at import/build/runtime. Most meaningful changes must be evaluated across four surfaces at once:

1. command declaration
2. provider schema/contract
3. SDK generation
4. REST serialization

A change that passes locally in one surface can still regress another because they share metadata but not identical execution wrappers.
